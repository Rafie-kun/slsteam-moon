# Running slsteam-moon with the 64-bit Steam client (steamrt64)

Steam now starts a 64-bit client by default (`steamrt64/steam`). `ld.so` refuses an
`ELFCLASS32` audit library in a 64-bit process, so the historical i386 `SLSsteam.so` is
ignored with

```
ERROR: ld.so: object '.../SLSsteam.so' cannot be loaded as audit interface:
wrong ELF class: ELFCLASS32; ignored.
```

and nothing is hooked. This document covers (1) restoring a working setup, (2) how the x86_64
build works, (3) which features are back and which are not, and (4) how to publish and
maintain the fix. Games stay 32- or 64-bit as before: only the *client* process is audited.

## 1. Restore a working setup

Verified on Debian 13, Steam client build `1794424036`, `steamrt64/steamclient.so` sha256
`53bdabbb…`. Another client build needs its locators checked first (section 4.3).

### 1.1 Back up first

Close Steam, then keep a copy of what the launcher can touch:

```bash
B=~/Backups/steam-before-slsm-$(date +%F); mkdir -p "$B"
cd ~/.local/share/Steam
cp -a steam.sh local.vdf "$B"/ 2>/dev/null
cp -a .steam-disable-steamrt64-client "$B"/ 2>/dev/null   # absent = 64-bit client already enabled
cp -a ~/.steam/registry.vdf "$B"/ 2>/dev/null
tar -czf "$B/config-vdf.tar.gz" config/*.vdf
```

### 1.2 Build the 64-bit library

```bash
sudo apt install g++ make libssl-dev libcurl4-openssl-dev      # amd64 headers, no :i386
make                       # ARCH defaults to uname -m; produces bin/SLSsteam.so (ELF 64-bit)
file bin/SLSsteam.so       # must say "ELF 64-bit LSB shared object, x86-64"
```

`ARCH=i386 make` keeps the old 32-bit build (it was not re-run when this port was written).

### 1.3 Install and launch

Intended path: `./setup.sh install`. It now reads the ELF class of the client that will
actually run and refuses to install a library of the other class. That path has not been run
end-to-end on a real install yet; what has been run is the minimal manual setup below.

```bash
mkdir -p ~/.local/share/SLSsteam ~/.config/SLSsteam
cp bin/SLSsteam.so ~/.local/share/SLSsteam/
cat > ~/.local/share/SLSsteam/steam-x64.sh <<'EOF'
#!/bin/sh
export STEAM_FORCE_CLIENT=steamrt64
export LD_AUDIT="$HOME/.local/share/SLSsteam/SLSsteam.so${LD_AUDIT:+:$LD_AUDIT}"
exec "$HOME/.local/share/Steam/steam.sh" "$@"
EOF
chmod +x ~/.local/share/SLSsteam/steam-x64.sh
~/.local/share/SLSsteam/steam-x64.sh
```

`STEAM_FORCE_CLIENT=steamrt64` makes `steam.sh` delete the sentinel
`.steam-disable-steamrt64-client`; the backup restores it.

### 1.4 Check that it works

```bash
grep -c 'Detour hooked' ~/.SLSsteam.log        # 30 on the verified build
grep -E 'CheckAppOwnership|RunIPCFrame' ~/.SLSsteam.log | head -3
ls -t /tmp/dumps | head -3                      # no new crash dump
```

Also confirm the webhelper is alive (`pgrep -a steamwebhelper`) and the Steam window loads.
`ld.so … wrong ELF class` lines in `~/.local/share/Steam/logs/console-linux.txt` are expected:
they come from 32-bit helpers (`ubuntu12_32/*`) that inherit `LD_AUDIT`.

### 1.5 Roll back

Close Steam, then restore the backup files (`steam.sh`, the sentinel, `local.vdf`,
`registry.vdf`, `config-vdf.tar.gz`) and remove `~/.local/share/SLSsteam/SLSsteam.so`,
`steam-x64.sh`, `~/.config/SLSsteam` and `~/.SLSsteam.log`. If the client itself is damaged,
delete `~/.local/share/Steam/steamrt64` and let Steam download it again.

## 2. How the x86_64 build works

| Problem | Solution | Where |
|---|---|---|
| Byte signatures of the i386 client do not exist | Whitelisted table of signatures, RTTI vtable slots and string xrefs, audited offline against the installed client (`make test-patterns-x86_64`) | `src/patterns_x86_64.hpp`, `src/rtti_vtable.hpp` |
| `la_objopen` runs before the module is relocated | RTTI vtables are read through the module's own `RELATIVE` relocations | `src/patterns.cpp` |
| libmem's trampoline can sit 5 GiB from the target and keeps RIP-relative operands unchanged | Own detour: trampoline within ±2 GiB, RIP/branch relocation, refusal of what cannot be relocated | `src/detour_x64.cpp`, `make test-detour-x64` |
| Struct layouts and hook signatures differ | `CServerPipe`, `CUtlBuffer`, `CNetPacket`, protobuf messages; handles as `uintptr_t`, `bool` returns, 32-bit params as `uint32_t` | `src/sdk/*`, `src/hooks.*` |
| SteamRT3 starts the client as `steam → srt-client-container → srt-bwrap → pv-adverb → steam` | `LD_AUDIT` is kept in the client chain and removed only in `steamwebhelper` | `src/main.cpp` |
| Wrong-class install | Class check in installer and generated wrapper | `setup.sh` |

Pitfalls found on the real client, each covered by a test:

- The webhelper branch of `setup()` runs before the log exists; `cleanEnvVar` used the null log
  and every `steamwebhelper` segfaulted, so Steam kept restarting (`make test-webhelper-audit`).
- The Steam process exports an `LD_LIBRARY_PATH` suffix that every child inherits (the file
  manager opened by "Browse local files" among them); it listed the 32-bit directories
  (`/usr/lib`, `/usr/lib32`), and `tools/library-inject`, when a wrapper puts it in `LD_AUDIT`
  (the 64-bit wrapper does not; a leftover or older one can), could hand a 64-bit process a
  32-bit `libcurl.so.4` on multilib systems (issue 5). The directories are now per architecture
  and ordered, and the redirect checks that each candidate is a shared object of the process's
  own ELF class and machine before returning it (`src/system_libdirs.hpp`,
  `make test-library-inject`).
- `searchOffsetByTypeName` wrapped its range check for a null vtable (`make test-memhlp-range`).
- `IClientUtils` is a secondary base of `CSteamEngine`: `getUtils()` searches `12CSteamEngine`.

## 3. Feature status

Verified in real sessions (account logged in; a Proton title, appid 1091500, launched from the
64-bit client with `CheckAppOwnership -> 1`, `Unlocked 1091500` and a cached depot key in the
log; it ran about two minutes and no crash dump was produced): 30 hooks installed, client
stable, and the licence/IPC hooks firing (`CheckAppOwnership` called over a thousand times,
`RunIPCFrame` tracing of `IClientUser`, `IClientConfigStore`, `IClientFriends`, …). Other
installed hooks (tickets, `RequiresLegacyCDKey`) were seen firing in an isolated trial but
nothing was asserted about their output.

Not restored yet — each line is a warning in `~/.SLSsteam.log`:

| Feature | State on x86_64 | What is missing |
|---|---|---|
| Manifest binding (`ProcessDepotManifest`, `PrepareDepotDownload`, `BuildDepotDependency` hooks) | ported and exercised: a never-installed, unowned title (Terraria, appid 105600, 607 MB, depot 105602) downloaded, committed and launched | `leaf` and `plan` redirect and fetch the manifest from the provider (`exact gid … ready from provider`); the `build` hook only ever saw an empty vector in the first call, so its in-place plan filtering is not proven |
| Reconcile pin | ported: entry hook on `EvaluateConfigChanges` (context flags +8, app id +0xc, depot vector base +0xc0 / size +0xd0) and the target-vector builder hook gated on its call site; installs at start | the pin rewrite and the empty-depot filter have not met a case that triggers them on a real client; the TARGET-side flag (bit 0x8) is assumed identical to i386 |
| Depot quarantine | ported: both copies of `OnChunkUnpacked` (0x13de1e0, 0x13de530) hooked, depot id read through the context (owner +0x10, depot pointer +0x18), chunk SHA at +0x10 | only reachable when three distinct chunks fail to decrypt; the context layout is deduced from the i386 one and checked with pointer plausibility, not seen live |
| App info cache provisioning | partly located | `GetOrAddAppData` and `ThreadedReadFromDisk` located and audited (hooks not ported); `SkipFlagReference`, `ShaReference` (code-shape references) not found |
| Package 0 injection (`PackagePatch`, boot path) | ported, exercised by the Terraria download above: package 0 gets the managed apps and depots, so Steam plans their depots | runtime hot reload is off: `MarkLicenseAsChanged`, `ProcessPendingLicenseUpdates`, `NotifyLicensesUpdated` have no 64-bit locator yet, so a game added while Steam runs needs a restart |
| Library removal | stubbed | 64-bit SteamUI protobuf layout |
| Licence refresh helpers | disabled | `CUser::NotifyLicensesUpdated`, `MarkLicenseAsChanged`, `ProcessPendingLicenseUpdates`, `m_CompatManager` |
| Parental, stats | hooks installed, not exercised live | `ParentalSignatureCheck`, `ParentalSettingsReceived` (only run with `DisableParentalRestrictions: yes`), `CAPIJob::GetPlayerStats` (locator audited offline) |
| UI overview | not ported | `BuildCompleteAppOverviewChange` is dead code on the 64-bit client; `CSteamUIAppController::*` has no x64 locator |
| CEF debug-port rewrite (needed by Lumen) | working | `la_symbind64` added; `make test-cef-rewrite-x64`; not yet seen with a real Lumen |
| SteamStub / DRM removal | disabled | helper not installed by the manual setup; to be verified through `setup.sh install` |

Exercised so far: ownership, tickets, IPC, package 0 injection and a full download of an unowned title. A title that needs DRM removal, quarantine of an undecryptable depot or live add without restart will not work yet.

## 4. Publishing and maintaining the fix

### 4.1 Pull request

Base branch: the project's default branch (`slsteam-moon`). Branch: `port/x86_64`, four commits:

1. `feat(x86_64): build and hook the 64-bit Steam client (steamrt64)` — the Makefile, SDK,
   hooks, locators and detour belong together and do not split by file.
2. `feat(setup): refuse to install a library of the wrong ELF class`
3. `test(x86_64): audit locators offline and exercise the real client`
4. `test: build test_ticket and test_fakeappid_wiring on x86_64`

PR description outline: what it fixes (`ELFCLASS32` on steamrt64, issue 9), what it does not
(section 3 table), verification (section 4.2 with real numbers), known limits (the i386 build
was not re-run; `test-package.sh` and the ELF32 gate of `package.sh`/`check-sls-abi.sh` fail on
a 64-bit binary; five tests remain red (section 4.2)).

### 4.2 Verification before opening it

```bash
make && file bin/SLSsteam.so
make test-patterns-x86_64 test-addr-plausible test-client-layout test-memhlp-range \
     test-detour-x64 test-webhelper-audit
for t in $(sed -n 's/^\(test-[a-z0-9-]*\):.*/\1/p' Makefile); do
  make -s "$t" >/dev/null 2>&1 && echo "PASS $t" || echo "FAIL $t"; done   # failures below are known
make loadtest-x64                                              # needs an installed Steam
scripts/trial-real-client-x64.sh                               # isolated copy, no network, 90 s
```

Last run of that loop: 81 targets, 76 pass, 5 fail. Known red tests: `test-familyshare`,
`test-fakeappid-presence` (stale `CNetPacket` API), `test-stats-provenance` (missing include),
`test-optional-locators` (expects a locator the installed i386 client no longer has),
`test-stats-audit` (checks the `la_symbind32` stats bridge; `la_symbind64` now exists but this
test still targets the 32-bit entry point). `test-thread-start` is flaky (red once out of three runs).

### 4.2b Packaging and installer

- `scripts/package.sh` names the zip after the build class: `slsteam-moon-linux-<ver>-x86_64.zip`
  for an ELF64 `SLSsteam.so`. `--host` makes a local test zip (`…-x86_64-host.zip`) from a host
  build; it skips the glibc 2.34 floor of `scripts/check-sls-abi.sh`, which stays enforced for
  releases (a Debian 13 build needs GLIBC_2.38). A release build must therefore go through the
  Ubuntu 22.04 container: `scripts/build.sh --portable` now picks `scripts/Dockerfile.x86_64`
  (no 32-bit toolchain) on a 64-bit host and runs docker as the calling user. That image has
  been written but not built yet.
- In the wrapper, `library-inject.so` (which redirects the 32-bit libcurl to a 32-bit system
  copy) is left out of `LD_AUDIT` for an ELF64 `SLSsteam.so`.
- `install-x86_64.sh` runs the stock luatools-moon installer with two functions replaced when
  the 64-bit client is in use: slsteam-moon comes from the `*-x86_64.zip` release asset or
  `--slsteam-zip FILE`, and CloudRedirect is skipped (32-bit hook) with `DisableCloud: yes`.
  Everything else (checks, Lumen, plugin, Game Mode, desktop coverage) is the stock code,
  sourced at run time. With the 32-bit client it delegates unchanged. `make test-install-x86_64`
  tests the selection logic against a stub installer; it has not been run against the real
  stock installer, Lumen or the plugin on this client.

### 4.3 When Steam ships a new client

Steam updates `steamclient.so` often; the locator table is pinned by evidence, not by guesses.

1. `make test-patterns-x86_64` — every locator must still resolve to exactly one function.
2. For one that does not: `tools/re/README.md` (in French) describes the RTTI / string-xref scripts used
   to re-derive it (vtable slot first, string xref second, byte signature last).
3. Update `src/patterns_x86_64.hpp` with the new evidence, re-run the audit on both
   `steamclient.so` and `steamui.so`, then run the real-client trial.

### 4.4 Rules for future changes

- No offset or signature without evidence from the client binary; an unresolved locator
  disables its feature with a warning instead of guessing.
- Anything in `setup()` that runs before the log exists must not use it.
- Keep the 32-bit game / 64-bit client distinction: the audited process is the client only.
